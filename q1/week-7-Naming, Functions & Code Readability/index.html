Naming, Functions & Code Readability
Clean Code, Chapters 2–3 — code is read far more often than it is written
What this is

Chapters 2 and 3 of Clean Code make a specific claim: naming and function design are not cosmetic. They are the primary way a reader reconstructs your intent without asking you. A codebase is read 10x more than it is written, so every name and every function signature is a small act of communication with a future reader — often future you, six months later, with no memory of the decision.

Naming — the core rules

A good name answers, without needing a comment: why this exists, what it does, and how it is used. Martin's rules that matter most in practice:

  • Intention-revealing: int d; tells you nothing. int elapsedTimeInDays; tells you everything.
  • Avoid disinformation: don't call something a List if it's not a List — don't call a group of accounts accountList unless it actually is one.
  • Pronounceable and searchable: genymdhms is neither. Single-letter names are only acceptable as loop counters in a very small scope.
  • Class names are nouns (Order, PaymentGateway), method names are verbs (calculateTotal(), notifyCustomer()).
  • One word per concept: don't mix fetch, retrieve, and get for the same kind of operation across the codebase.
Functions — the core rules

Martin's function rules are more radical than most developers apply in practice:

  • Small, then smaller: functions should rarely exceed 20 lines; many good ones are 4–6.
  • Do one thing: a function does one thing if you cannot meaningfully extract another function from it with a name that isn't just a restatement.
  • One level of abstraction per function: don't mix "parse the JSON payload" (low-level) with "process the order" (high-level) in the same function body.
  • Few arguments: 0–2 is ideal, 3 needs justification, 4+ is almost always a sign that a parameter object is missing.
  • No flag arguments: a boolean parameter that changes behavior means the function does two things — split it into two functions.
  • No side effects: a function named checkPassword() that also starts a session is lying about what it does.
Senior framing: naming and function size are not style preferences — they are the mechanism by which a codebase stays changeable. In your Hexagonal Architecture context, a port interface with vague method names (process(), handle()) forces every implementer and every reader to open the implementation to understand intent. That's a direct tax on the "explain the tradeoffs" ability your 1-year target requires.
Naming — before / after
Bad — disinformation, non-searchable, unclear intent
public class OrderService {
    public void proc(Order o, int t) {
        List<Item> list1 = o.getItems();
        double x = 0;
        for (Item i : list1) {
            x += i.getPrice() * i.getQty();
        }
        if (t == 1) {
            x = x * 0.9;
        }
        o.setTotal(x);
    }
}
Good — intention-revealing, searchable, verb-based method name
public class OrderService {
    private static final int DISCOUNT_TIER_LOYAL_CUSTOMER = 1;
    private static final double LOYAL_CUSTOMER_DISCOUNT_RATE = 0.9;

    public void calculateOrderTotal(Order order, int customerTier) {
        double subtotal = sumItemPrices(order.getItems());
        double total = applyDiscountIfEligible(subtotal, customerTier);
        order.setTotal(total);
    }

    private double sumItemPrices(List<Item> items) {
        double sum = 0;
        for (Item item : items) {
            sum += item.getPrice() * item.getQuantity();
        }
        return sum;
    }

    private double applyDiscountIfEligible(double amount, int customerTier) {
        if (customerTier == DISCOUNT_TIER_LOYAL_CUSTOMER) {
            return amount * LOYAL_CUSTOMER_DISCOUNT_RATE;
        }
        return amount;
    }
}
Flag arguments — before / after
Bad — boolean argument hides two behaviors in one function
public void sendNotification(String message, boolean urgent) {
    if (urgent) {
        smsGateway.send(message);
    } else {
        emailGateway.send(message);
    }
}
Good — split into two functions with intention-revealing names
public void sendUrgentNotification(String message) {
    smsGateway.send(message);
}

public void sendStandardNotification(String message) {
    emailGateway.send(message);
}
Splitting the flag-argument function does not mean duplicating logic — if both paths share steps, extract a private helper. The point is that the caller's intent should be visible in the method name it calls, not buried in a boolean literal at the call site (sendNotification(msg, true) tells the reader nothing without checking the signature).
Traps that show up at senior level
1. Renaming without understanding. A common mistake under review pressure is renaming a variable to something that sounds better without verifying it's still accurate. userList renamed to userCollection when it's still a List is meaningless churn; renamed to activeUsers when it actually is filtered — that's the real fix.
2. Small functions with hidden coupling. Breaking a large method into many small private methods is good — but if those methods all mutate the same instance field in sequence and must be called in a specific order to work, you've just hidden a temporal coupling problem behind clean-looking names. This is worse than one long function, because the danger is no longer visible.
3. "One thing" is a judgment call, not a line count. A function that validates an object's five fields is still doing "one thing" — validation — even if it's 20 lines. A function that validates and then persists is doing two things, even if it's 8 lines. Extraction should follow responsibility boundaries, not an arbitrary line limit.
4. Command-Query Separation as a naming discipline. A method should either do something (command, verb, void or side-effecting) or answer something (query, returns a value, no side effects) — never both. boolean save() that returns whether the save succeeded but also performs the save violates this and makes call sites ambiguous: if (save()) reads like a query but is a command.

    public boolean proc(String uid, String msg, int t, boolean f, boolean log) {
        boolean ok = false;
        String x = "";

        if (t == 1) {
            x = "Dear customer, " + msg;
            ok = emailClient.send(uid, x);
        } else if (t == 2) {
            x = msg.length() > 160 ? msg.substring(0, 160) : msg;
            ok = smsClient.send(uid, x);

            x = msg;
            ok = pushClient.send(uid, x);

        if (f) {
            if (t == 1) {
                x = "URGENT: " + msg;

            ok = emailClient.send(uid, x);
        }

        if (log) {
            System.out.println("Notification sent to " + uid + ": " + ok);
        }

        return ok;

Test your understanding

1. Why is a boolean flag argument considered a design smell, not just a style issue?

Because it means the function has at least two distinct behaviors selected by the caller, which violates "do one thing." It also makes call sites unreadable (process(x, true) tells you nothing without opening the signature) and increases test complexity, since every flag combination is a separate path to verify.

2. A function is 45 lines long but only validates a DTO's 12 fields, one check per line. Does it violate "do one thing"? Why or why not?

No. "One thing" is about responsibility, not line count. Validation of one object is a single responsibility even if it takes many lines. Splitting it into 12 tiny methods just to satisfy a line-count instinct would fragment a cohesive operation for no readability gain.

3. What's wrong with a method named getUser() that also updates the user's lastAccessedAt timestamp as a side effect?

It violates Command-Query Separation and, more directly, the naming rule that a name must not lie about what the function does. "get" signals a pure query with no side effects; a caller has no reason to expect a write is happening, which makes the codebase harder to reason about and easier to break during refactors.

4. You have a method with 5 parameters, three of which are always passed together (street, city, zipCode). What's the fix, and what principle does it point back to?

Introduce a parameter object — an Address class grouping street, city, and zipCode. This reduces the parameter count and, notably, connects back to SRP: if those three values always travel together, they likely represent a concept that deserves its own type rather than being scattered as primitives.

5. Why does Martin prefer verbs for method names and nouns for class names, and what breaks when that convention is ignored?

A class represents a concept or entity (noun), while a method represents an action performed on or by it (verb) — reading order.calculateTotal() mirrors natural language. When ignored (e.g. a class named Process, a method named data()), the reader loses the grammatical cue that normally tells them, without documentation, whether they're looking at a thing or an action.
